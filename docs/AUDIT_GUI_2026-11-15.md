# Audit of 2026-11-15: the window (`hxex.gui`)

The first audit of the Qt window: bugs, quality, speed and memory, as of commit b91c54d (the last
green commit before the profile-fit merge; the picking check tab of 13957ad is therefore out of
scope and is covered in the first fix session that touches the Results workspace). Six bug
reviewers, one per disjoint scope, each read every line of its scope and its tests and reproduced
every CONFIRMED finding with a pytest-qt script on the pinned export; a quality reviewer read the
whole package and the guide against the window; a measurement job timed the window on four real
projects. Every High item was then reproduced a second time by a fresh agent that got the item's
text and the export only, not the reviewer's script. PLAUSIBLE items were verified by reading the
code only. The emphasis, as in the earlier audits, is on what hurts the user: a wrong file written,
edits lost, a wrong spectrum or sample shown as another, crashes and hangs in realistic paths, and
the window disagreeing with the command-line outputs. Nothing in the repository was changed.
Decisions are left to the owner; the layout follows docs/AUDIT_2026-11-01.md so that a decision can
be recorded beside each item. The reproduction scripts, logs and measurements are kept privately
(see "Where the evidence is").

Baseline: at b91c54d the 238 GUI tests pass when each file is run alone, ruff is clean, CI green on
all 11 jobs. The window is about 12,900 lines in 29 modules under `src/hxex/gui/` with 168
offscreen tests in 16 files, plus the command-line pieces built for it (`--progress-format json`,
`--stop-from-input`, `python -m hxex`). No Critical finding (nothing corrupts a bundle or loses a
run's results); the worst classes found are a write to the wrong project's files after a project
switch and project files written as invalid TOML by ordinary edits.

Datasets: the tutorial data (published), the intact-peptide benchmark, the private targeted
Orbitrap dataset (fragment ions, Thermo .raw through .NET, the elution tab) and the private pooled
dataset (mzML, pooled forms, saved elution windows); every job that writes worked on a copy.

Severity (Part 1): High = wrong file written, user edits lost, wrong spectrum or sample shown as
another, crash or hang in a realistic path; Medium = wrong in an edge case, misleading display,
state left over after a switch, inconsistency with the command-line outputs; Low = cosmetic,
wording, latent hazard. Part 2 (quality) uses Major = a reader of the code or the guide is misled,
or a user-reachable path has no test; Minor = polish.

## Cross-cutting themes (the audit's reading; each item is listed under its scope)

1. **State that belongs to the previous project survives a switch.** The window resets its
   views on a project switch but not the loads, computations, histories, pending writes and
   folders keyed to the old project: a results load still arriving (A-1), a Compute still running
   (E-1, E-3), the elution editor's Undo history (D-5, F-4), decisions waiting for a held table
   (D-7), the export folder (E-10), the sequence view's counts and residues-a-line (E-13, E-24), a
   Recompute flag (E-23). Three of the thirteen High items are this. One rule closes them: every
   workspace receives the new project or results path in `show_results`/`show_project` and drops
   everything keyed to the old one (the `Latest` runners, the cancel events, the histories), and
   a result arriving later is accepted only when its path is still the one shown.
2. **Work in flight is never cancelled.** The library's analysis takes a cancel hook and never
   calls it (E-1, E-11); trace reads take none (F-6); superseded drawings run to the end in the one
   drawing thread (C-12; M measured 44 s of drawing after the last key of a held arrow), and the
   close waits 10 s for them, blocked (A-5, A-13, E-11). PLAN "GUI" rule 6 asks for hooks; the
   fix is in the library (hooks checked per table, figure, file and spectrum) and in `_Job`
   (skip a job whose ticket is no longer the latest).
3. **The window keys things by weaker identities than the data's own.** Sample, range and charge
   without the sequence (C-7); `id()` of a tuple that is freed (C-11); the `Results` object's
   identity for the spectrum being edited (F-2); row numbers that a sort moves (C-4); the raw
   spectrum-id cell (D-1); an HX-Express file name that drops the channel and the modification
   (E-2). The data's own keys (spectrum id, `data_id`, sequence, read record) are available in
   every case.
4. **Writes without a check of what the reader will accept.** The editor writes text it cannot
   parse (B-1); a dialog's overwrite question is asked for the name without its extension (B-4);
   a decision is written into a table with duplicated ids that the commands then refuse (D-1); a
   level-1 save adds a second row for the same ion (D-4); several series go to one export file
   (E-2). One rule: never write what the project's own reader refuses (parse the TOML, run the
   table reader, check the final file name), and refuse with the reader's words.
5. **The project file is edited line by line with patterns that do not know TOML.** Comment lines
   starting with `[` read as headings (B-1, B-2), quoted keys and quoted headings with spaces are
   not found (B-5, B-7), a multi-line list swallows the next setting (B-1), continuation comments
   are not recognised (B-24), a switched-off setting is left behind when its entry moves (B-8),
   and switching a stage off and on loses its settings (B-6). `hxex set` shares the misreadings
   (it refuses where the window writes). A TOML-aware pass over the file (or a round-tripping
   library, open question B 7) fixes the family at once.
6. **The window and the command line disagree.** Compute analyses a review K that `hxex analyse`
   refuses (E-4); a decision the bundle's layer holds shows as cleared but is not (D-2); a K the
   screen skipped is accepted and then stops the project from opening (D-9); UTF-16 tables and
   separator guesses differ from the readers' (D-12, D-14); Copy rounds to four digits where the
   tables keep six (C-3); a linked project file resolves `[analysis]` paths differently (E-25).
   PLAN "GUI" rule 1 (the window shows what the commands would write) wants the window to call
   the same reader and the same refusal in each case.
7. **Structure (Part 2, Q).** Six routes write the project file and only one keeps Undo and pauses
   the watcher (Q-1); the file is parsed in fourteen places with two readers (Q-2); decision and
   file-format logic sits in `hxex.gui` against rule 1 (left-out reasons, the elution-window
   writer, the review table's `review_K = 0` rule: Q-4); the GUI imports private library names
   (Q-5); `review.py` promises no Qt but needs it (Q-6). The tests: two files open windows on the
   screen when run alone (Q-25), one depends on test order (Q-26), about thirty user-reachable
   actions have no test (Q-27); the hang of HISTORY 365 did not recur in three passes.
8. **Speed (Part 2, M).** With the data tab hidden a selection blocks the window at most 24 ms;
   shown, 0.26-0.65 s on every large project, because `spectra_table` and `uptake_table` cost
   0.2 s whatever the rows asked for. Opening the benchmark takes 14 s to the flat list, 8 s of it
   in `spectra_table` for the list's rows in the background and 1.75 s of
   `QTableView.resizeColumnsToContents` in the window thread. Rendering to PNG is 55-70 % of the
   drawing thread's time. Compute with ladder rates: 63 s, all in `fit_decay`'s `curve_fit`
   calls (3,766 of them). Reopening a project in one window does not leak; a new window per
   cycle keeps its whole results alive (61-301 MB per cycle), which matters for test sessions.

## Open questions

### A. Lifecycle, threads, processes

1. `hxex run --overwrite` or `resume` started from the Run tab while the Results workspace holds
   the same bundle: results load lazily (PLAN, rule 6) and the bundle is replaced file by file at
   publish (HISTORY 72), so a figure drawn at that moment could read a half-replaced bundle.
   Should the window close the results (or refuse to draw) while a run or resume of the project
   is running? (`run_command` does not look at `window.loading` either.)
2. Two windows on one session file (or one project): the last save wins silently (atomic
   replace, so no corruption); both watch the review table and reload on each other's
   decisions. Intended?
3. The stop semantics of a close (A-5): should the window wait asynchronously and show what the
   command is doing, and should the question name the abort and kill that follow?
4. A stop during the fit stage leaves nothing on disk (tutorial copy, `repro_13`): `resume`
   finishes a stopped bootstrap but not a stopped fit. Outside this scope; the close question
   ("a bootstrap stopped part way can be finished with Resume") is right, but a user may expect
   the fits so far to be kept.
5. `_Stop.early` (cli.py 316, 358) is never reset once set; one command per process makes it
   harmless, but a process running two commands in turn would stop the second at once.
6. `MessagesHandler` is attached to the `hxex` logger per window: with two windows in one
   process (tests) each pane shows both windows' messages until one closes.

### B. Project editor and user tables

1. Should the window's `unfinished` mode ever write text that does not parse? (Proposed in B-1:
   never.) And should it write a change whose new problem names another key of the same table?
2. Switching a stage off comments the tables and lists under it (`[review]` off comments the
   `[[review.exclude]]` rules). Is that intended, and should on restore what off switched off (B-6)?
3. Saving a table drops blank lines, strips spaces around column names and normalises quoting
   (real tables of all four projects round-trip byte for byte, so only hand-made files change).
   Acceptable?
4. Semicolon tables are saved with commas, but decimal commas ("12,5") stay text and fail the
   reader's check at Save. Convert them, or only say so?
5. Should a read-only table (or one in a read-only folder) be refused with its own message (B-11,
   B-20)?
6. New table on a kind that already names an existing table: replace (today, after the dialog's
   question), or refuse and open the existing one?
7. `hxex set` shares B-1's and B-2's misreadings (it refuses rather than writes). Fixing
   `project_edit` fixes both; is a TOML-aware round-tripping library acceptable as a dependency,
   or should the line editor be extended?

### C. Results tree, list, figure view, data tab

1. PLAN says a click on a spectra-page panel selects that spectrum. Results only shows the gid on the status bar, and its help says the Results figures have no click-through. Is the click still wanted?
2. A peptide row shows its first charge's figures and data rows, while its review covers every charge. Should the data tab list all charges?
3. The data tab's uptake.csv rows ignore `[figures] k` and `corrected`, but the guide calls them "the values of its uptake page". Should the tab say it shows the CSV?
4. A bundle opened on its own uses the default analysis settings for "left out". Should the tree say so?
5. Should the List keep its current row across a reload? It keeps the sort and the column filters.

### D. Review and the files the window writes

1. D-2: should the window be able to clear a decision the bundle's layer holds? It needs a
   reader convention (an explicit "unreviewed"); without one the honest display is "rejected
   (bundle)" with the status disabled.
2. D-8: at choice 2, should the edited file's other charge states give up their own rows (as
   they do in the spread files), with the same question as the spread asks?

is not freed: its C++ objects are deleted (`shiboken6.isValid` False after the deferred delete was
delivered), but the Python side of the window, its workspaces, its results and its four figures
(overview cache, a spectrum's panels) stay alive, so every closed window keeps its whole results
(about 60 MB for the tutorial data, 300 MB for the benchmark). `leak_diag.py` shows the closed
`MainWindow` wrapper referenced only from inside its own cycles (ResultsWorkspace,
AnalysisWorkspace and TableZoom `__dict__`s, `ProjectEditor` holding the bound method
`sample_names`, a `Latest` callback closure from `open_results`), and many widget wrappers held by
references the garbage collector cannot see (shiboken's parent/child ownership), so those cycles
are never collected; the logging handler was removed and no `_Job` was left. The `hxex gui`
process makes one window and ends with it, so this matters for long test sessions and any
process that makes several windows; the measurement harness itself first leaked for another
reason (deferred deletes are not delivered by `processEvents` outside an event loop), which
`measure.py` now handles.

high-water and matplotlib caches rather than retained figures; not followed further.
