## Cross-cutting themes (the audit's reading; each item below is listed under its module)

1. **Python exceptions reach the user.** `_dispatch` in `cli.py` catches a fixed set of
   exception types; `KeyError` (section typos, `[figures] series`, `corrected` without controls),
   `TypeError` (tables written as `false`), `xml.etree.ElementTree.ParseError` (a stale mzML index),
   `UnicodeDecodeError` (a cp1252 project file) and pyarrow's `FileNotFoundError` (a damaged bundle:
   the whole message is a bare path) all escape or print without a sentence. One boundary rule
   would close most of them at once: catch the specific ones where they arise with a sentence
   naming the file and the fix, and catch everything else once in `_dispatch` with "hxex stopped
   with an internal error (TYPE: text); please report it with the log", so the user never sees a
   traceback.
2. **The data's own labels are not checked against the user's inputs.** The folder name's
   sequence against the FASTA (Readers 3), the peptide table against the folder name (Part 2 B4),
   FASTA files and folders that do not pair up (Readers 14), a lowercase FASTA cut by characters
   (Readers 15), `samples` or `peptide_ranges` matching nothing reported as "every spectrum was
   dropped" (Readers 13). Each is a silent wrong answer or a false "ok" from `hxex check`.
3. **`hxex check` passes what `hxex run` or a later command refuses.** No control of any kind
   with `[run.controls]` on (Settings 8), a table row whose charge has no files (Readers 12), a
   duplicated table row (Readers 10), `k_max = 1` with the analysis's default `ks` (Settings 4),
   a review table naming spectra the bundle does not have (Part 2 M7), `resume` saying "nothing to
   add" when the review chooses a K the bundle never fitted (Settings 5). The check should run the
   same validations the commands do; `hxex check` printing its problems before the status block
   and ending without "ok" / "not ok" (Part 2 M1) compounds it.
4. **Statistical rules applied to too few values.** The m/z check's scatter from three offsets
   (Picking 24: a 4 ppm offset flags a series, which the analysis then leaves out by default),
   the control replicate-outlier limit from one replicated time point (Picking 25: a good replicate
   dropped in a tenth of such runs), `fd_disagrees` judged against a rejected control (Picking 26),
   the analysis replicate-outlier limit set by the outlier itself (Analysis Low 26), 40-bin
   histograms for two series (Report 43). A common rule, "no scatter estimate from fewer than N
   values; say not assessed instead", would fix the family.
5. **Work lost or left stale around the bundle.** `--keep-previous` after the fit (Bundle 4), an
   interrupted replacement that cannot be written again (Bundle 18) and loses its review on the
   next overwrite (Bundle 19), tables refused after the fit (Bundle 20), `resume BUNDLE` leaving
   the tables stale while the guide says it rewrites them (Bundle 21, Settings 6), `[output]
   tables` resolving to the bundle folder (Settings 10).
6. **Small datasets break the analysis.** A sample with controls only or no K = 2 description
   stops `hxex analyse` (Analysis 5), `k_max = 1` is refused with no way named (Settings 4),
   `ks = [1]` refused unless `overlay` changes (Analysis Low 22), a promoted control loses its
   population test (Analysis 34). Pilot projects and tutorial-sized runs are exactly what a new
   user tries first.
7. **Figures that mislead.** Colours wrapping onto the reference (Report 6), replicate styles
   repeating after six (Report 41), the spectra page never marking a rejected or flagged spectrum
   although it is the page drawn for flagged series (Report 39), the significance maps' legend
   over the axis labels (Report 40), corrected values clipped on the population map (Report 44).
8. **Reproducibility.** A measurement's fit depends on the other measurements in its batch
   (Engine 28): on a GPU the chunk plan follows the free memory at run time, so a rerun or a
   resume is not bit-identical and K can flip at the margin. The `FitConfig` docstring promises
   independence.

# Part 1: code audit and bug search

## High

### Settings and command line

1. **A mistyped `[run.SECTION]` heading is a KeyError traceback** (`config.py:268` →
   `_section_class` `:208`). `[run.fitt]`, `[run.piker]`, `[run.bootsrap]`: the unknown table is
   merged into the run settings as a Mapping, and the loop that re-validates each section does
   `_hints(RunConfig)[name]` on it. The user gets a 30-line traceback ending `KeyError: 'fitt'`
   from `hxex check`, `run`, `report`, `resume` and `analyse` alike (KeyError is not in
   `_dispatch`'s exception set), while a mistyped key inside a known section is reported cleanly
   ("[run.fit]: unknown fit setting(s): k_mx"). CONFIRMED (`s_typo2`). *Fix:* in `run_config_from`,
   before merging, `_check_keys(data, set(_hints(RunConfig)), "[run]")` (or skip `_section_class`
   for keys RunConfig does not know and let `RunConfig.from_dict` name them).

2. **A top-level table written as `false` is a TypeError traceback** (`config.py:923` for
   `analysis = false`, `:529` for `input = false`, `:781` for `output = false`; `:970-971` for
   `[analysis] regions = false` and `sites = false`). The template's first lines say "false stands
   for 'not set' where a setting can be unset", so a user who wants to switch the analysis off
   writes `analysis = false` and gets `TypeError: argument of type 'bool' is not iterable`.
   `figures = false`, `review = false` and `run = false` are refused cleanly ("[figures] must be a
   table"). CONFIRMED (`e1`, `e2`, `e3`, `c22`, `e9`). *Fix:* one check in `project_from` that
   every top-level table (`input`, `run`, `output`, `analysis`, `figures`, `review`) is a Mapping
   ("[analysis] must be a table; to turn the analysis off, delete the table"), and `_none`/`_items`
   for `regions` and `sites` (a list or false).

### Readers

3. **A SpecExport FASTA that disagrees with the peptide folders is used without a word**
(`io/specexport.py:81-107` `scan_specexport`: `_RANGE_DIR` ignores the folder's sequence;
`cli.py:_check_peptides` only tokenises). HDExaminer names every peptide folder
`START-END-SEQUENCE`; hxex cuts the sequence from the FASTA by the range and never compares it
with the folder's. With a FASTA whose numbering differs from HDExaminer's (an expression tag or
signal peptide the FASTA includes, a construct from another project, a mutant folder beside a
wild-type FASTA), every entry gets the wrong sequence and so the wrong m/z: all spectra come
out "without signal" or fit garbage. CONFIRMED: `r2_folders.py` section A (folder
`0002-0005-KVLA`, FASTA with a four-residue tag: hxex reads `GGGM`); `cli/tag.toml`:
`hxex check` prints `ok`, `hxex run` ends with `every spectrum was dropped (empty, without
signal or without bins)` and no hint about the sequence. A point-mutant FASTA beside the wrong
folder would be worse: only the peptides over the mutation are wrong, and they fit something.
*Fix:* in `scan_specexport`, parse the folder's own sequence (the text after `START-END-`)
when it tokenises; when it differs from the cut (compare base residues, ignoring modX labels
and termini), log a warning naming the folder, the two sequences, and the FASTA, and have
`hxex check` list every such folder as a problem ("the folder names SEQ, SAMPLE.fasta gives
SEQ2 at residues A-B: the FASTA's numbering differs from HDExaminer's"). The guide line "the
sequence in the folder name is not used" should become "is checked against the FASTA".

### Bundle, run stage and outputs

4. **`--keep-previous` moves the old bundle only after the fit, and a failed move loses the
   whole run** (`run.py:1068-1072`: `move_previous(out)` is called after `_fit_part` at
   `:1041`; `io/bundle.py:729-732` moves the bundle, then `name_tables`, `name_figures` and the
   analysis folders one `os.replace` after another, with no rollback). If any move after the
   first fails (on Windows a folder cannot be renamed while a file in it is open: a CSV of
   `results_tables` open in Excel is the ordinary case; a permission error anywhere else), the
   bundle has already gone to `results.N`, `results` no longer exists, the exception propagates
   out of `run()` and nothing of the new run is written: the fit (and, with a bootstrap, the
   checkpoint that would have followed) is lost, and the folders are half moved
   (`results.1` beside `results_tables`). CONFIRMED (`e_keep_previous_fails.py`: `os.replace`
   made to fail for `res_tables`; afterwards `res` is gone, `res.1` exists, `res_tables` stays,
   the run raised `PermissionError`, no new bundle). The same ordering applies to the CLI,
   since `cmd_run` relies on `run()` for the move.
   *Fix:* do the moves right after `_previous()` succeeds and before any picking or fitting
   (`hxex run` promises to refuse "before anything is fitted"; the move belongs there too), and
   make `keep_previous` transactional: on an `OSError` undo the moves already done (reverse
   order) and raise a `BundleError` naming the folder that could not be moved ("close the files
   open in it"). If the move must stay late, catch the failure and write the new bundle under
   `<name>.new` with a warning rather than discard the fit. Test: a failing second move leaves
   every folder where it was and no fit is attempted.

CONFIRMED: `s01` (the reference reviewed to one population: `compare_peptides(K=2)` and `write_analysis` raise; the population quantity returns `one population (both)` as it should), `s11` (a non-reference sample reviewed to one population: the same crash). *Fix:* resolve the reference and the wanted samples on the states present at K = 1 (the time-point rows, as `_lever_sides` does), and give a state without records at `(K, rank)` no rows (or rows with `reason = "no K=2 (sample)"`), never an error; the same in `compare_residues` (resolve on the K = 1 residue keys). ### Engine (model, fit, noise, bootstrap, population test)

28. **A measurement's fit depends on the other measurements in its batch, so the chunk plan (and
on a GPU the free memory at run time) changes fits and, at the margin, K**
(`fit/optimise.py:142-183` `run_adam`, `fit/polish.py` `lm_polish`, `model/mixture.py:438-441`
`nll`; `run.py:294-303` `default_budget`, `:307-336` `plan_chunks`). The k-means start of a
measurement is bit-identical alone and in a batch (batch_start.py), and the loss of that start
differs only by rounding (1e-13 in float64, 3.7e-4 in float32, from the reduction over a
different padded width), but 150 Adam steps and the polish amplify it: fitting 12 spectra of
four widths alone and together gives `|nll alone - together|` up to 0.025 (float32, the
default) and 9e-4 (float64), with p differing by 0.005 (batch_independence.py); padding every
spectrum to the same width does not remove it (batch_source.py "same_width True": 0.031), so it
is the optimiser's chaos on rounding, not the padding. 0.025 in nll is 0.05 in BIC, enough to
flip K where two Ks are within that, which HISTORY 46 put at a few spectra per thousand for a
rounding change of the same size (float32 against float64). The batch a spectrum is fitted in
is the chunk `plan_chunks` makes from the memory budget: 4 GiB on the CPU (stable) but half the
FREE GPU memory at run time (`default_budget`), so the same project on the same GPU chunks
differently when another process holds memory, and a rerun after excluding spectra or a
`hxex resume` that refits "the series the test's screen fits differently" (`run.py:~700-726`,
a different batch) is not bit-identical to the original. CONFIRMED (synthetic). The
`FitConfig` docstring ("a measurement's fit depends only on its own data, its noise reference
and the seed, not on the other measurements in the batch") promises more than holds. *Fix:*
make the chunk plan a function of the data and settings only (a fixed default GPU budget, or
record the plan in the manifest and reuse it on resume), state the rounding caveat in the
docstring and the guide's reproducibility text, and recommend `dtype = "float64"` where
bit-level reproducibility across machines matters.

### Engine (model, fit, noise, bootstrap, population test)

- Binomial pmf (`log_binom_pmf`, `_log_binom_integers`, `_integer_log_pmf`) against
  `scipy.stats.binom` for integer n and the gamma form for real n, normalised to 1e-15
  (float64) and 4e-7 (float32), p from 0.02 to 1 - 1e-7 through the logit path (numerics.py 1).
- BIC `3K ln(max(N, 2)) + 2 nll` and AIC `6K + 2 nll` (numerics.py 2); N = bins (Gaussian) or
  scaled counts (Poisson); the controls' extra K = 1 never selected; smallest K when every K
  fails `min_population`; `can_win`'s reach uses the same penalty and N as the criterion.
- Per-bin variance `z b1 I + (m I)^2` at the three-bin edge-aware mean, floored at
  `(0.005 top)^2`, enters the loss as `0.5 (pred - obs)^2 / var` exactly: the fitted `nll` of
  a charge-3 spectrum equals the independent sum from the fitted parameters to 1e-6
  (numerics.py 3); the same raw-unit variances reach the polish (`model.weight`), the screen
  floor (weighted NNLS, a valid lower bound of the K = 1 and K = 2 losses), the bootstrap
  (`sqrt(var)/scale` as the draw's sd and `var/scale^2` as the refit's weights, boot_null.py)
  and the null (`simulate_null` passes `w*w` with scale 1).
- `model_error` is a percent in `NoiseConfig` and a share in `ControlsNoise`; the division
  happens once (`fit/models.py:204`, `run.py:410, 501`). `b1` is per unit charge
  (`_residual_design` column `charge x intensity`, `variance` multiplies by charge).
- Smoothing after Medium 20: `[1000, 300, 50, 5, 0]` gives 650 at bin 0 (edge-aware mean).
- `gamma_tail` with moments (3, 6) equals `chi2.sf(t, 3)` to 1e-6; a flat null gives 1/0 by
  the mean (and is no longer tested); NaN moments give NaN (numerics.py 4). The simulated
  null's variance is ddof = 1 (boot_null.py); `statistic_of` clips negatives and rounding to 0
  and keeps NaN.
- `steps_K` stops at the first step that does not reject; a screened step (`added` NaN) never
  adds a population; the test never selects a K that was not fitted.
- k-means start keeps the cluster mean where n is clipped (HISTORY 176: a wide weak spectrum
  gives n at its cap and n p equal to the cluster mean minus the shape's mean, kmeans_check.py);
  a bimodal spectrum starts at the two modes; one bin at K = 3 gives finite, deterministic
  jittered copies; an all-zero spectrum starts finite.
- `split_start` halves the heaviest amplitude and shifts the logit by +-delta.
- Edge inputs through `fit_models` (edge_inputs.py): one bin, two bins, bins not starting at 0
  (gather path), n_max 1.2, tops of 1e9 and 1e12 with the percent scale (identical fits in
  scaled units), negative intensities (Gaussian) and an all-zero spectrum under one sd per
  spectrum all give finite fits and K = 1 where appropriate, with no crash; 1e12 with `sd = 1`
  in float32 keeps finite losses of 1e20.
- Thread count does not change the fits: 40 spectra at K = 1-3 in float32 and float64 give
  bit-identical losses and the same K with 1 and 4 CPU threads (threads.py).
- The population test on synthetic one- and two-population spectra (boot_null.py): the
  simulated null's mean and variance (ddof 1) equal those of the stored `null_draws`; a
  spectrum with T = 409 reads p = 0 and two populations, one with T = 0 reads p = 1; the test's
  K and the criterion's agree; the chi-square null gives the same K; the step-two draws of the
  two-population spectra are small (0.2-2), as they should be.
- Device choice: `auto` is CUDA when available else CPU; an explicit `cuda` without CUDA raises
  before any work; the report's curves are NumPy (`report/curves.py`), so a GPU-fitted bundle
  is analysed and drawn on a machine without CUDA; `resume` takes `device`.
- Seeds: distinct streams for warm jitter `[seed, 1, key]`, random restarts `[seed, 2 + r,
  key]`, bootstrap draws `[seed, 3, it, key]`, null draws `[seed, 11, k, s, key]` and the
  k-means jitter `(seed + key) mod 2^31`, keyed by the measurement's identity.
- Bootstrap: components matched by mean with NaN draws given the identity order; the K = 5
  assignment path; `average_se` from each draw's weighted mean (smaller than the combined
  position errors); fixed-K results agree with the selected-K bootstrap row for row; failed
  draws counted out by `ok`; percentiles need two successes.
- Non-finite protection in Adam (restore and mask), L-BFGS (fallback to the pre-L-BFGS fit),
  the polish (a step is taken only if finite and lower), restart merge by loss.
- Cancellation: Adam every 25 steps, the polish every 5, each restart, each bootstrap resample
  and each null simulation; by reading, the progress total of `fit_models` counts the
  controls' K = 1 and the extra k-means restart for `k_min` 1 and 2 (the 2026-10-28 audit's
  "(7, 8)" Low could not be reproduced from the current code).
- `FitResult.merge`/`select`, `PopulationTest.merge`/`select` and `BootstrapResult.merge`/
  `select`/`scatter` keep row order and the per-bin curve equality (`_key` treats NaN as equal).

### Pain points

#### Blocking (would make a new user give up, or draw a wrong conclusion)

**B1. Editing the 470-line template by "find" lands on the wrong line, and the error points elsewhere** (tutorial step 4; project-file.md).
What happened: the template has four `d2o_fraction` lines (`[analysis.controls]` line 88, `[analysis.fragments.exchange]` 143, `[analysis.labelling]` 151, `[run.controls]` 376). Ctrl+F from the top finds the `[analysis.controls]` one first, and the tutorial's instruction ("find the part that starts with `# [run.controls]` ... delete the `# ` in front of the `d2o_fraction` line") is easy to carry out on the wrong `d2o_fraction` because every one of them is a commented line with the same comment ("D atom fraction of the labelling buffer"). The result is `unknown key(s) in [output]: d2o_fraction`: the uncommented line is read under `[output]`, the last live heading 300 lines above, which the user never touched. No line number, no hint. A user who does not know how TOML headings work has no way to connect `[output]` with the line they edited, and nothing else in the guide explains it (first-project.md says "A heading's settings are the lines below it, up to the next heading", which is true but does not cover commented-out headings).
Expected: the error to name the line, and to say that the line sits under a heading that is still commented out.
Recommendation: (a) when an unknown key is found, report the line number and check whether a commented `# [table]` heading precedes it: "`d2o_fraction` on line 88 was read under `[output]` because the heading above it, `# [analysis.controls]` on line 87, is still commented out: remove its `# ` too, or comment the line back out"; (b) make the template's duplicate keys distinguishable (the `[run.controls]` comment could read "labelling buffer D fraction used by the back-exchange correction"); (c) in the tutorial, give the line's exact text and say "the one under `[run.controls]`, near line 376, not the earlier ones under `[analysis...]`".

**B2. The tutorial promises that `hxex report hxex.toml --figures --overwrite` changes the tables; it does not** (tutorial step 9; project-file.md "What each one does"; outputs.md "Running again").
What happened: after the review table was switched on, `hxex report hxex.toml --figures --overwrite` redrew the figures only. `results_tables/spectra.csv` still said `unreviewed` for the rejected spectrum, `review.csv` was not written, and `uptake.csv` still averaged four replicates at 30 min. The tutorial says "The tables changed too." project-file.md's table says `hxex report` writes "the figures (`results_figures`), and the tables again"; the `--figures` row of the "Running again" table says it writes only `results_figures`. The command's own help says "draw the figures, and write the tables again". A user who follows the tutorial and then opens `spectra.csv` to confirm their decision sees it was ignored, and may conclude the review table does not work (or, worse, carry on with tables that do not reflect the review).
Recommendation: either make `--figures` also rewrite the tables (then `--overwrite` must cover `results_tables`, which `hxex check` already says), or change the tutorial and the two guide tables to say `hxex report hxex.toml --tables --figures --overwrite`, and make `hxex report` print "tables not written (add --tables)" when a review is in effect and only figures were requested.

**B3. The weak spectrum the tutorial asks you to reject is fine; what is wrong with WT 68-75 is something else, and the figures hide it** (tutorial steps 8-9; populations page).
What happened: on the spectra page of `WT_0068_0075_MRLEKDRF_z_2.pdf`, 30 min rep 2 has an intensity of 44,000 against 1.8-2.3 million for its replicates, and that is the only visible difference: the envelope is clean and fits with one population. The other 21 spectra of the series carry the `bright` flag (series.csv: `n_flagged 22`), and every 4 s, 1 min, 30 min, and 20 h replicate is fitted with two populations (n_multi 15), with the second population at 1 min and 20 h lying beyond the right edge of the populations page's axis, above the fully deuterated level (the `max_fD` filter later removes those K = 2 descriptions in the analysis, silently as far as the run's tables are concerned). The 20 h spectra are called two populations when the FD control, at the same level, is one. A scientist following the tutorial rejects the one spectrum that is probably the most honest of the series, and learns nothing about the `bright` flag on the other 21, which the guide's step 9 does not mention.
Recommendation: the tutorial's review step should use this peptide to teach what the user actually faces: the `bright` flag, and the K = 2 fits above full deuteration (both visible in the tables). The populations page must show components that fall outside the axis (extend the axis to the largest component, or draw an arrow at the edge with the value). The spectra panels should carry their flags and K in the panel title (`30 min, rep 2 (K=1, low_intensity)`) so the reader does not need `spectra.csv` open beside the PDF.

#### Major (costs more than a few minutes, or needs the author)

**M1. The run's progress estimate is wrong by a factor of five, and the bootstrap prints nothing for minutes** (tutorial steps 6 and 10).
What happened: `fit: 45% after 30s, about 37s left`, then `60% after 1m 32s, about 1m 01s left`, done after 3 min 48 s: the estimate assumes K = 2 and K = 3 cost the same as K = 1. The bootstrap printed `bootstrap: started` and then nothing for **25 minutes** (on a machine shared with other jobs; the guide says "prints its progress and the time left" and the default progress interval is 30 s), and its first line read `2% after 25m 20s, about 25h 42m left`. The analysis said `2% after 5s, about 4m 17s left` and finished 13 s later. A new user cannot tell a slow step from a hung program, and the 25-hour estimate would make most of them press Ctrl + C (which, before the first resample is written, throws the whole bootstrap away).
Recommendation: print a progress line at the interval even when no batch has finished ("bootstrap: 0 %, first resample in progress, 3 min elapsed"), weight the fit's estimate by K (or estimate per K), and do not print an ETA until the rate is stable (or cap it: "more than an hour").

**M1b. `hxex report hxex.toml --overwrite` (tables only) prints nothing** (project-file.md: "on its own, `hxex report hxex.toml` writes only the tables").
What happened: five seconds, no output, exit 0. The user does not know whether the tables were written, where, or whether the review was applied (it was: `review.csv` appeared).
Recommendation: print the same closing line as the figures path: `tables in .../results_tables (review: 1 rejected)`.

**M2. The template is 470 lines of developer vocabulary, and the user must edit it by hand** (project-file.md; tutorial steps 4, 8, 9, 10, 11).
What happened: the file the tutorial asks a non-programmer to edit cites Python classes (`hxex.picking.PickerConfig; docs/PEAK_PICKING.md`, `hxex.fit.FitConfig`, `hxex.noise.NoiseConfig`), developer notes ("12 was fastest on a 24-core CPU", "as before 2026-10-31"), and many settings with no meaning to a user (`grad_clip`, `lbfgs_steps`, `split_delta`, `kmeans_after_warm`, `resolving_power_exponent`). The six tutorial edits are at lines 5, 22-26, 48-49, 292-308, 327/376, 450-470: a lot of scrolling in Notepad, and each is "delete the `# `" on a particular line among look-alikes (see B1).
Recommendation: a short template by default (`hxex init` writes only the settings a user changes: project, input, output, controls, bootstrap, review, analysis, figures, with the three stage tables present but switched off by a plain `enabled = false`), and `hxex init --full` for the present file. Alternatively `hxex set run.controls.d2o_fraction 0.85` style commands, so the tutorial never asks for a text edit. Strip the Python class names from the comments.

**M3. Four `hxex report` / `hxex analyse` invocations in a row, every one needing `--overwrite`, and the first time it is refused** (tutorial steps 8-11; first-project.md).
What happened: steps 9 and 10 each redraw; forgetting `--overwrite` costs a refusal with a four-clause message. `hxex resume` then warns that `results_figures` is stale. The flow is: change the file, remember which command, remember `--overwrite`. `[output] overwrite = true` would end it, but the tutorial never suggests it.
Recommendation: tell the tutorial reader in step 9 to set `overwrite = true` in `[output]` once ("you will run these commands many times"), or make `hxex report` and `hxex analyse` overwrite their own folders by default (they are cheap to recreate; the refusal matters for the bundle).

**M4. `hxex info results` says `review none` right after the user made a review** (project-file.md commands table).
What happened: the review table is a project-file setting, the bundle's review layer is empty, and `info` reads the bundle. The user cannot tell the two apart; `info` does not mention the project file.
Recommendation: `hxex info hxex.toml` (accept the project file, as every other command does) and report both: "review: none stored in the bundle; the project's review table user_review_table.csv rejects 1 spectrum".

**M5. The spectra and populations pages have no legend** (tutorial step 8; outputs.md).
What happened: the orange line, the dashed blue and green lines, the black sticks, the grey picking-window band, the orange star on the populations page, the circles/squares/diamonds in the "replicates" column, the dotted vertical lines, the up and down triangles on the uptake page: none is named on the figure. The guide explains the spectra page in prose ("The black sticks are the measured isotope peaks, the line through them is the fit") and the triangles nowhere ("rep 1-4" is the only legend). The populations page's title overlaps the "UN, rep 3" panel title.
Recommendation: one legend per page (fit / population 1 / population 2 / picked peak / raw / picking window; K = 1 mean (star); low-D (up) and high-D (down) population), and a K label per panel.

**M6. The overview's controls and quality pages are unreadable without the guide** (tutorial step 8, "The overview").
What happened: the controls page has unlabelled dashed lines (orange at 0.25, black at 1.1), a bar chart whose categories are flag names (`fd_retention_agrees (flag only)` reads like a warning but is good news), and a histogram of "m0 (deuterons beyond natural abundance)". The quality page's middle panel ("misfit / series median" against "intensity / mean of the other replicates", colour = flagged share, "sparse cells as points") is a developer's diagnostic. The tutorial text describing the page is accurate but 15 lines long, and the numbers it quotes (192 measured, 3 fell back) are the figure's only accessible content.
Recommendation: label the dashed lines on the axis ("outlier limit", "retention_max"); write the categories in words ("retention agrees with the other samples (information)"); drop or simplify the misfit-intensity panel for users (keep it under `-v` or a `developer` figure).

**M7. CSV values are written with 16 significant digits** (tutorial step 7).
What happened: `retention 0.4865089041514463`, `mean_1 0.0036541559618291086`. In Excel these show as 0.486509, fine, but the files are 1.1 MB for 3,874 rows and every number looks like noise when the CSV is opened in a text editor or pasted into a notebook.
Recommendation: round to 4-5 decimals in the CSV tables (the bundle keeps full precision).

**M8. "Note the version you used" is impossible: every install reports `hxex 0.0.1.dev0`** (install.md "Updating hxex").
Recommendation: put the commit hash or date into `--version` (`hxex 0.0.1.dev0 (b3595cf, 2026-11-01)`) and into `manifest.json` / `run_settings_used.toml`.

**M9. The tutorial's figure of the file tree does not match the download** (tutorial step 1).
What happened: the tree shows `Non-1-z2.csv`; the files are `Non-D-1-z2.csv` and `Full-D-1-z2.csv`, and the folder also has `0.1s-*` and `0.8s-*` files, which inputs.md's "Times and controls" table does not show as a valid form (it shows `30s`, `5m`, `1.5m`, `4h` and says `250ms` is refused). A user checking their own export against the guide would doubt `Non-D` and `0.1s`.
Recommendation: show the real names, and add `0.1s` to the table of accepted time tokens.

**M10. The first `hxex check` after an error does not end with the verdict** (first-project.md step 5).
What happened: the problem lines (`input.data_dir ...: no such directory`, `1 problem(s) found`) are printed before the summary, and the summary ends with `outputs none yet: hxex run writes results`, not with `ok` and not with the problem. The guide's example shows the problem as the last lines. In a real terminal the problem scrolls up out of view behind the summary.
Recommendation: print the summary first and the problems (with the count) last, or repeat the count as the last line.

**M11. The run's own K = 2 decisions and the analysis' decisions differ, and the user sees only one of them** (tutorial steps 6, 9, 11; statistics.md).
What happened: the run says 875 spectra have two populations (overview, spectra.csv), the review step talks about `review_K`, and then the analysis quietly removes 1,497 + 552 + 164 + ... K = 2 descriptions (min_population, max_fD, max_fD_se) and decides per peptide-and-time with `best_set_K`. The tutorial mentions `best_set_K` once, at the end. A user who read `spectra.csv` first believes the 875.
Recommendation: say early (step 7) that the spectrum-level K is provisional and the number to report is `best_set_K` (or the population test's), and consider adding a `best_set_K` column to `uptake.csv` so the run's tables carry the decision too.

### Open questions for the author

1. **WT 68-75 (data_id 107):** all 21 unrejected spectra are flagged `bright`, every labelled replicate selects K = 2, and the second population at 1 min and 20 h sits above the fully deuterated control (`max_fD` removes those descriptions in the analysis). ### Pain points, by severity

#### Blocking

**B1. `[run.contrls]` (any misspelt nested section under `[run]`) crashes with a traceback (c03).**
`KeyError: 'contrls'` from `config._section_class`. A user who misspells `[run.controls]`,
`[run.fit]` or `[run.picker]` sees twenty lines of Python and no hint.
Recommendation: validate the sub-table names of `[run]` like the keys of every other table.
Message: `unknown table [run.contrls] in hxex.toml: the tables of [run] are run.picker,
run.fit, run.fit.noise, run.fit.backend, run.bootstrap, run.population_test, run.controls,
run.quality, run.registry, run.envelope (did you mean [run.controls]?)`.

**B2. The Python page's first snippet fails as written (Part 2, below).** After
`hxex.load_project(...)`, `hxex.run` is the `hxex.run` submodule, not the entry point, so
`hxex.run(spectra, project.run, ...)` raises `TypeError: 'module' object is not callable`. A
programmer following the page literally gives up at line 4. (Details and fix in Part 2.)

**B3. A sample with only controls stops `hxex analyse` for the whole project (t03).**
`no sample 'D109H' in the results (samples: R120G, WT)` is false (series.csv lists it) and
the analysis writes nothing. A control-only sample is ordinary (a sample whose labelled
runs are still to come, or a shared control sample), and the user cannot guess that
`[analysis] samples = ["WT", "R120G"]` is the way out.
Recommendation: leave such samples out of the analysis with one warning: `D109H has no
labelled time points (controls only): left out of the analysis`. If it must stop, name the
fix: `... add [analysis] samples = ["WT", "R120G"] to leave it out`.

**B4. A peptide table that contradicts the folder names is accepted silently (p10, p11).**
With `[input] peptides`, a sequence (`...VLGE` for a folder named `...VLGD`) or residue
numbers (88-97 for `0087-0096`) that differ from the folder name pass `hxex check` with
`ok`. The fit then uses the wrong composition, or the residue map is shifted by one, with
nothing in any output to show it. inputs.md promises a warning only for a `peptide_range`
label that differs.
Recommendation: when the folder name carries a range and a sequence (SpecExport and pooled
always do), compare and warn in `check` and `run`: `peptides.csv line 5: the sequence
EELKVKVLGE differs from the folder's name (0087-0096-EELKVKVLGD): the table's sequence is
used` and likewise for the numbers; count them as problems in `hxex check` unless a new
column or setting says the table is authoritative.

#### Major

**M1. Problems are printed at the top, before the status block (c15, c17b, p07-p09, t01).**
`hxex check` prints the problem line(s) and `N problem(s) found` first, then twelve lines of
settings and entries. The last line a user sees is `outputs none yet: hxex run writes
results`, with no `ok` and no "not ok". A new user scanning the end of the output can miss
the problem; first-project.md's example shows the problem and `1 problem(s) found` as the
last lines, which is not what happens.
Recommendation: print the problems after the status block and end with `not ok: 1 problem
(above)`, or repeat the count as the final line.

**M2. A damaged bundle gives a bare path as the whole message (q09, q09c).**
Deleting `fit.parquet` makes `hxex info results` and `hxex report` print just
`results/fit.parquet`. A user cannot tell whether this is an error, a file it wrote, or a
file it wants. With `spectra.parquet` gone, `hxex info` still says `raw spectra stored`.
Recommendation: `results is not a complete bundle: results/fit.parquet is missing (a bundle
is the whole folder hxex run wrote; run again with --overwrite)`, and make `info` report
`raw spectra: file missing`.

**M3. Commands given the wrong kind of file or run too early do not name the right step
(q02, q02b, q03, q03b, q04).** `results is not a bundle directory or zip` (before any run),
`hxex.toml is not a bundle directory or zip` (`hxex info hxex.toml`), `notes.txt: not valid
TOML (Expected '=' ...)` (`hxex run notes.txt`), `cannot read hxex.toml: [Errno 2] No such
file or directory` (wrong folder), and argparse's `the following arguments are required:
PROJECT`. Each is true; none says what to do.
Recommendation:
- `hxex report/analyse/info` on a missing bundle: `no results yet at /.../results: run
  "hxex run hxex.toml" first (it writes the bundle this command reads)`.
- `hxex info hxex.toml`: `hxex info takes the results folder, not the project file: hxex
  info results`.
- not valid TOML on a file that is not `.toml`: prefix `hxex run needs the project file
  (hxex.toml, written by hxex init); notes.txt is not one:`.
- missing file: `no hxex.toml in /current/folder: open the terminal in the project folder,
  or run hxex init to write one`.
- argparse: `metavar="hxex.toml"` and a help line "the project file".

**M4. A semicolon-separated or wrongly-cased peptide table reports "missing columns" (p03,
p05).** Excel in many countries writes `file;sample;peptide;...`; the message lists all six
columns as missing. `Charge` for `charge` is "missing column(s) charge".
Recommendation: when the header has one column containing `;`, say `peptides.csv: the
columns are separated by semicolons; save it with commas (Excel: CSV UTF-8, or File > Options
> Advanced > list separator)`. When a required column is present in another case, say
`column 'Charge' should be 'charge' (lower case)`. In all cases print the columns found.

**M5. `[run.controls]` on without undeuterated controls says nothing about the correction's
missing undeuterated end (k01, k03).** The fully deuterated case gets `no fully deuterated
control was accepted, so ... no back-exchange correction`; the undeuterated case gets only the
noise-reference warning. series.csv marks every series `m0_missing` and `control_fallback =
True`, but the user who read back-exchange-correction.md expects to be told what m0 was
used (and that `mean_corrected` is then on a different footing).
Recommendation: a parallel line: `no undeuterated control in this run: the undeuterated end
of every series is taken as 0 D (m0_missing): mean_corrected assumes no undeuterated
background`.

**M6. The sections of `hxex check` for a misspelt heading or a key under a commented
heading (c00, c01).** `unknown key(s) in the project file: imput` treats a heading as a key
and does not say that `[input]` is now missing (the reader goes on to use the default
`data_dir`?). `unknown key(s) in [output]: d2o_fraction` for a key the user wrote under a
`# [analysis.labelling]` heading they forgot to uncomment is the most likely way a user hits
this (the template invites it), and the message points at the wrong section.
Recommendation: `unknown table [imput]; the tables of the project file are input, output,
review, analysis, run, figures (did you mean [input]?)`; and for a key that exists in some
other table: `[output] has no setting d2o_fraction (it belongs to [run.controls] or
[analysis.labelling]); the heading above it, line 158, is still commented out?` (the line
number of the key is known from the TOML parse position; at least name the other tables).

**M7. `hxex check` lets a review table with a wrong `spectrum_id` pass, and counts it (q10a).**
`check` reports `2 spectra: 2 rejected` and `ok` for a table whose second rejected id does
not exist; only `report` warns, and still counts 2. A user who mistypes an id in a 5,000-row
table believes the spectrum is rejected.
Recommendation: `check` (which already opens the bundle for `outputs`) should match the ids
and print `1 row names a spectrum these results do not have (hspb5:WT/.../99h-1-z2.csv)` as
a problem; the counts should exclude skipped rows.

**M8. `[run.fit]` and `[run.controls]` range errors are written in notation (c22, c23).**
`d2o_fraction must be in (0, 1]` and `need 1 <= k_min <= k_max`.
Recommendation: `d2o_fraction = 85: write the D2O fraction as a number between 0 and 1
(85 % is 0.85)`; `k_min (3) is larger than k_max (2): k_min is the fewest populations tried
and k_max the most`.

#### Minor

### Part 2: the Python page (docs/guide/python.md)

Run in a plain `.venv/bin/python -I` process with `MPLBACKEND=Agg`, in a copy of the

#### The snippets as written

1. **"A run" fails at `hxex.run(...)`.** `hxex.load_project` and `hxex.read_input` work
   (`Project`, `SpectrumSet`). Then `hxex.run(spectra, project.run, out="results",
   project=project.project)` raises `TypeError: 'module' object is not callable`. Cause:
   `hxex/__init__.py` resolves `run` lazily through `__getattr__`, but `load_project`
   imports the `hxex.run` submodule, and Python then binds `hxex.run` to the module, which
   wins over `__getattr__`. (Accessing `hxex.run` *before* `load_project` caches the function
   and the snippet works: an order-dependent trap.) Workaround: `from hxex.run import run`.
   Fix: do not let a submodule and an entry point share a name (rename the entry point, e.g.
   `hxex.run_project`, or expose the function as `hxex.run.run` and write the page that way),
   or import the entry points eagerly in `__init__` after the submodules. Every snippet below
   it on the page depends on this one, so a reader following the page gets nothing without
   the workaround.
2. **With the workaround** (`import hxex.run as m; m.run(...)`) every other snippet of "A
   run" works: `open_bundle` + `Results.from_bundle`, `write_tables(results,
   "results_tables")` (four CSVs and the listing) and `write_figures(results,
   "results_figures", PlotConfig(series="all"))` (12 series PDFs and `overview.pdf`). The
   "Reviewing spectra" snippet works with real ids (`bundle.review()` is an empty
   `ReviewTable`, `update(...)` returns a new one, `set_review` writes it); with the page's
   made-up id (`my_protein:WT/0001-0011-LKDVEHFKVSS/30s-1-z2.csv`) `set_review` raises
   `BundleError: review entries for unknown spectra: [...]`, which is clear. Two things a
   user would stumble on: `print(result)` or `print(results)` dumps the whole dataclass tree
   (every array of every spectrum; the log of this script is 1.6 MB for 237 spectra), so the
   objects cannot be inspected at the prompt; and `write_tables`/`write_figures` overwrite an
   existing folder without the command line's refusal.
3. **Logging.** From Python nothing is printed but library warnings (`dropped 1 of 326
   spectra ...`, `per-bin noise: too few ...`) via Python's last-resort handler, without
   timestamps, and no progress. The page should say so and show the two lines that give the
   command line's output (`import logging; logging.basicConfig(level=logging.INFO,
   format="%(asctime)s %(message)s")`).
4. **The pooled snippet** on a SpecExport folder: `scan("SpecExport", "pooled",
   sample="pool")` returns `[]` silently; `scan("SpecExport", "specexport")` returns the 12
   `PeptideEntry` objects and `match_candidates(entries, "SpecExport/WT.fasta")` yields
   `m.entry.peptide, m.matches` as the page shows (`MDIAIHHPW ('WT',)`). The snippet works;
   an empty list for a wrong format is the only trap.
5. **Imports the page does not show.** `open_bundle` is written `from hxex.io import
   open_bundle` in one place and `hxex.open_bundle` in another (both work). The things a user
   needs next (`series_table`, `uptake_table`, `find_series`, `load_results`, `show_series`)
   are not on the page at all; `load_results` and `show_series` exist (the notebook uses
   them) and are the right entry points for a notebook user, but a reader of this page cannot
   find them.
